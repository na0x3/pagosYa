## Assumption verification (2026-09-16)

- **Base URLs** `https://sandbox.dlocal.com` / `https://api.dlocal.com` — CONFIRMED. <https://docs.dlocal.com/reference/api>
- **Headers** `X-Date` (ISO-8601), `X-Login`, `X-Trans-Key`, `X-Version: 2.1`, `Content-Type: application/json`, `Authorization: V2-HMAC-SHA256, Signature: <hex>` — CONFIRMED. <https://docs.dlocal.com/reference/payins-security>, <https://docs.dlocal.com/docs/generate-signature>. Note: docs also list a `User-Agent` header as required on every request; the brief's list omitted it (see corrections section).
- **Signature** = hex HMAC-SHA256(secretKey, `X-Login + X-Date + body`) — CONFIRMED, exact concatenation order and algorithm documented. <https://docs.dlocal.com/docs/generate-signature>. The "body `""` for GET" detail is UNVERIFIED — the docs only show POST examples and don't state the GET body value explicitly; kept the assumed empty-string behavior.
- **`POST /payments` body** `amount`, `currency`, `country`, `payment_method_id`, `payment_method_flow` (`DIRECT`/`REDIRECT`), `payer {name,email,document}`, `order_id`, `notification_url`, `callback_url`, `card {token}` — CONFIRMED, all present (among a larger field set). <https://docs.dlocal.com/reference/create-a-payment>
- **Payment response** `id`, `amount`, `currency`, `status_detail`, `redirect_url`, `order_id` — CONFIRMED. **Status enum — CORRECTED**: real top-level values are `PENDING`, `PAID`, `REJECTED`, `CANCELLED`, `AUTHORIZED`, `VERIFIED`. There is no top-level `EXPIRED` status; "The payment was expired." is a `status_detail` string, and an expired voucher/redirect payment resolves to `CANCELLED` (confirmed pattern via dLocal Go help center), not a distinct `EXPIRED` status. Old assumption: status enum included `EXPIRED` → New: use `CANCELLED` for expired vouchers. <https://docs.dlocal.com/reference/payment-status-codes>
- **`GET /payments/{id}`** — **CORRECTED**: does not return the same shape as the create-payment response. It adds `payment_method_id`, `payment_method_type`, `payment_method_flow`, `country`, `card`, `created_date`, `approved_date`, `status_code`, `notification_url`, `refunds` (array), optional `enrollment`/`retry` — and it does **not** include `redirect_url`. Old assumption: identical shape to the create response → New: richer payload, no `redirect_url`. <https://docs.dlocal.com/reference/retrieve-a-payment>
- **`GET /payments-methods?country=XX`** returns `[{id, type, name, logo, allowed_flows}]` — CONFIRMED exactly. `type` enum is `CARD`, `BANK_TRANSFER`, `DIRECT_DEBIT`, `TICKET` (no `WALLET`). <https://docs.dlocal.com/reference/search-payment-methods>, <https://docs.dlocal.com/reference/payment-method-object>
- **`POST /refunds` body** `{payment_id, amount, currency, notification_url}` — CONFIRMED. **Response — CORRECTED (expanded, not contradicted)**: response includes `id`, `status`, plus `status_code`, `status_detail`, `payment_id`, `order_refund_id`, `amount`, `currency`, `created_date`, `amount_refunded`, `use_orig_fx`, `payment_request_amount`, `payment_request_currency`, `transaction_id`, `authorization_code`, `document_number`, `order_id`, `notification_url`. Refund `status` values are `PENDING` / `SUCCESS` / `REJECTED` — a **separate enum from payment status** (payment statuses are `PENDING`/`PAID`/`AUTHORIZED`/`REJECTED`/`CANCELLED`/`VERIFIED`). <https://docs.dlocal.com/reference/refunds>, <https://docs.dlocal.com/reference/refund-status-codes>
- **Notifications** POSTed to `notification_url` with the payment object as body and the same signature headers — CONFIRMED. <https://docs.dlocal.com/docs/receive-notifications>
- **Webhook `amount`/`currency` echo the requested USD values (not the shopper's local currency)** — UNVERIFIED. Docs describe an opt-in `currency_to_charge` field for charging the shopper in their local currency; when it is not set, the `amount`/`currency` fields are expected to reflect the requested (merchant/USD) currency, but no doc page explicitly states this for the notification payload. Kept the assumed value.

## Contract corrections for later tasks

1. **No top-level `EXPIRED` payment status.** Real statuses: `PENDING`, `PAID`, `REJECTED`, `CANCELLED`, `AUTHORIZED`, `VERIFIED`. An expired/unpaid voucher resolves to `CANCELLED`, not `EXPIRED`. Affects **Task 6** (status-mapping table in `DlocalAdapter`: map `CANCELLED` → `failed` for the voucher-expiry case, don't look for `EXPIRED`) and **Task 8** (webhook handler must not special-case an `EXPIRED` status that never arrives).
2. **`GET /payments/{id}` is not shape-identical to the create-payment response.** It omits `redirect_url` and adds `payment_method_type`, `created_date`, `approved_date`, `refunds`, etc. Affects **Task 6** (status mapping / `getStatus` must not assume `redirect_url` is present on a GET) and **Task 9** (reconciliation worker calls `getStatus`, must not depend on `redirect_url` to detect a `requires_action` payment on poll — that info is only available from the original create/redirect response).
3. **Refund `status` is a distinct enum from payment `status`.** Values are `PENDING`/`SUCCESS`/`REJECTED`, not the payment status set. Affects **Task 6** (refund result mapping in `DlocalAdapter.refund`).
4. **`User-Agent` header is also required** alongside the headers listed in the brief. Affects **Task 5** (`DlocalClientService` must set a `User-Agent` header or dLocal may reject/flag the request).
