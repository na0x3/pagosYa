# YAPI personalizes the product card — Design and Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Program:** sub-project 5 of `docs/superpowers/specs/2026-09-29-themed-product-card-program.md`. **Prerequisites (done and committed, in this order):** `2026-09-29-photo-sets-and-content-blocks.md`, then `2026-09-29-product-card-theme-and-guarded-css.md`. This plan uses `resolveProductTheme`, `PRODUCT_CARD_PRESETS`, `sanitizeProductThemeCss` and `checkProductTheme` from that plan; do not start until they exist.

**Goal:** When YAPI designs or edits a store it also chooses that store's product-card identity (a preset, tuned DNA dimensions and a few lines of guarded CSS), verifies it, and stores it so two different businesses end up with visibly different product pages.

**Architecture:** The store's design lives in `SourceDesign` (`concepts[selected].dna`, `apps/api/src/storefront-source/source-design.ts`, `source-dna.ts`), and `sourceRuntimeDna(dna, storeId, productPageStyle)` (called around `source-generation.service.ts:821`) turns it into `config.dna` for the runtime. We extend that pipeline (model schema → `normalizeDna` → `sourceRuntimeDna`) with the `productCard` group and `productCss`, teach the prompts, and give the agent engine a tool `set_product_card_theme` whose result is merged into the accepted design. The browser check runs inside the agent's `verify` step.

**Tech Stack:** NestJS (jest). All new code is TypeScript in `apps/api/src/storefront-source/`.

## Design

1. **Model path (concept generation).** `SOURCE_DNA_SCHEMA` (used as `dna` in `sourceDesignSchema`) gains `productCard: { swatch, gallery, blocks, divider, enter }` (enum values from `SOURCE_DNA_ENUMS.productCard`) and `productCss` (`string`, max 3000). Both are filled with defaults by `normalizeDna` when absent (`plain` preset params, `productCss: ''`); when the model returns `productCss`, `normalizeDna` runs `sanitizeProductThemeCss`, keeps only the sanitized CSS, and appends each dropped item to the `repairs` list (existing mechanism: `repairs` strings are prefixed and collected by `validateSourceDesign`). Absent `productCard` for an **existing** design must normalize to the defaults without adding a repair (old designs stay valid).
2. **Runtime config.** `sourceRuntimeDna` copies `productCard` and `productCss` into the object that becomes `PAGOSYA_CONFIG.dna` (names match the runtime: `swatch`, `gallery`, `blocks`, `divider`, `enter`; see the theme plan D1). Nothing else about the config changes.
3. **Prompts.** `SOURCE_PRODUCT_PRESENTATION_DIRECTION` (in `source-design.ts`, line ~10) and the DNA instructions (find where `SOURCE_DNA_SCHEMA` fields are explained to the model: `git grep -n "buttons.form\|surfaces.card" -- apps/api/src/storefront-source | grep -v spec`) gain a compact section: the eight preset ids with their `when` text, the cosmetic parts list, the allowed-property summary, the protected controls and why, "choose the preset by what the business sells, then tune at most three dimensions, then write at most 20 rules of `productCss`, using `--pd-*`/`--brand-*` tokens so the theme follows the store's colours", and the rule that content blocks are merchant-supplied and only framed by the theme (never invent block content). Include one worked chair-shop example (`workshop` + `productCss` restyling `[data-part="gallery"]`, `[data-part="thumb"]`, `[data-part="block"][data-part-type="compare"]`).
4. **Agent engine tool.** New tool in `agent/agent-tools.ts`: `set_product_card_theme` with strict-schema parameters `{ preset: enum|null, swatch: enum|null, gallery: enum|null, blocks: enum|null, divider: enum|null, enter: enum|null, css: string|null }` (the `tool()` helper marks every property required, so unused values are `null`). The toolbox calls `resolveProductTheme({ preset, params, css })` (no browser at this point), stores the result in `toolbox.pendingTheme` (`{ productCard, productCss } | null`) and returns the report as text (`dropped` items and the final param values) so the agent can iterate. `AgentToolName` gains `'set_product_card_theme'`; `AGENT_TOOLS` and the agent prompt (`agent/agent-prompt.ts`) describe it in Spanish like the other tools.
5. **Verify step.** `verifyAgentDraft` (or `AgentToolbox.run('verify')`) gains a `theme` finding source: when `pendingTheme?.productCss` is non-empty, open the draft's product page in the same Playwright capture the agent already uses for `screenshot` (`agent/agent-capture.ts`), apply the pending `productCard`/`productCss` to the runtime config, run `checkProductTheme`, and report every failure as `{ source: 'theme', message: '<control> (<viewport>): <reason>' }`. A failing theme is **removed** from `pendingTheme.productCss` (DNA params stay) and the agent is told, so a draft with a broken theme can never be "clean". Add `'theme'` to the `AgentFinding['source']` union.
6. **Merge into the design.** Where the agent engine's result becomes the accepted design (around `source-generation.service.ts:654-821`, `sourceDesignAfterSectionEdit` and the call to `sourceRuntimeDna`), if `toolbox.pendingTheme` exists, write `productCard` and `productCss` into `acceptedDesign.concepts[acceptedDesign.selected].dna` **before** `sourceRuntimeDna` runs. A section-scoped edit (`sectionScope` set) may still call the tool only when the merchant's instruction mentions the product page/card/ficha (reuse the instruction-matching style of `sourceSectionScope`); otherwise the tool returns an error string ("Este pedido no cambia la ficha de producto.") and stores nothing.
7. **Reorder blocks (optional, Task 5).** YAPI may reorder a product's existing content blocks (never create, edit or delete them). Study how YAPI already applies product operations from an instruction (`source-product-options.ts`: `requestedSubscriptionOperations`, variant operations, and where their results are applied via the payment-links service) and mirror that flow for a `blockOrder` operation carrying `{ productId, order: string[] }`. If applying it needs more than adding one operation type to that existing flow, skip the task and say so in the final report.
8. **Merchant safety.** No new UI. Reverting is the existing revision history / "Deshacer" (each YAPI edit is a new revision); confirm in the final report that a themed revision can be undone (a one-line manual check or an existing test, state which).

## Global Constraints
- Old designs/stores keep working: a design without `productCard`/`productCss` normalizes to defaults with **no** repair message and renders exactly as before.
- YAPI can only choose preset ids and enum values from `SOURCE_DNA_ENUMS.productCard`, and CSS only through `sanitizeProductThemeCss`. Never widen the sanitizer in this plan.
- Protected controls are never styled by YAPI; the only defence is the sanitizer + `checkProductTheme` from the theme plan. Do not add a bypass.
- The tool description and prompts stay in the language the neighbouring text uses (agent tool descriptions in Spanish, prompts as in `source-design.ts`).
- **NEVER** run prisma migrate/db push or touch a database; **never** run the real YAPI eval script against the model API (it spends credits; the owner runs it). Do not run the full storefront-source suite; run the named specs one at a time. Playwright specs run alone; if browsers are missing, say so and stop that task after writing code and tests.
- pnpm at this repo root; never pnpm/commit in `/Users/saramia/pagosYaWeb`. Commit after each task; no push/merge; stage only your own files.

## Review Focus
1. **Old design objects** without the new fields validate and produce no repairs (Task 1).
2. **Model returns hostile CSS** (`url(`, `@import`, `pointer-events`): stored CSS is sanitized, drops appear in repairs, nothing unsafe reaches `config.dna` (Task 1).
3. **Tool called with `null` everywhere** is a no-op that says so, not an error (Task 3).
4. **A broken theme never ships as "clean"**: verify reports it, removes the CSS, keeps params (Task 4).
5. **Section-scoped edits** that don't concern the product card cannot change the theme (Task 4).
6. **Two contrasting businesses** end up with different themes (Task 6, unit level).
