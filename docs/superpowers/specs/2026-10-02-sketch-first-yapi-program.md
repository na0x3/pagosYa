Status: approved by the owner 2026-10-02 (conversation). Sub-project 3 (Boceto API + Studio panel) built 2026-10-02: GET/PUT `source-project/sketch` save deterministic revisions; the Studio's Boceto button opens an instant hand-editing panel (blocks, text, photos, colours, fonts, sizes, order, add/duplicate/delete). Templates retired as an offer the same day (chat + UI entries). Sub-project 4 (chat-on-sketch + explicit Construir + polish) pending.

## Why

Watching Figma Make build "The Bake Lab" from one line, the owner identified what pagosYa lacks: the AI's first output is a *design you can shape by hand* — click a headline and retype it, click a card and restyle it — and the risky build happens once, after approval. Today YAPI builds real code on every message: each request costs 80–300 s and 260k–660k input tokens (everyday-suite eval, 2026-10-02), and failures surface mid-conversation. The 2026-10-02 reliability fixes (ship drafts that build, soft findings stop early) cut the damage, but the architecture still puts the fragile step first.

Decision: for **new stores and full redesigns**, YAPI first produces an editable **sketch**; the real site is built deterministically from the approved sketch. Small edits to an already-built store keep today's direct flow.

## Decisions (made with the owner)

1. **Scope: new stores + redesigns first.** Not every request; not a user-facing toggle.
2. **Sketch format: design-blocks JSON.** Palette (3–5 colours with roles), fonts (display/text ids from `source-font-catalog.ts`), global scale, and an ordered list of blocks, each `{ id, type, variant, content fields, bg token, size }`, filled with the merchant's real photos and copy. Generated by one structured-output call against a strict schema — fast and effectively failure-proof.
3. **Edit depth (day one): text, photos, colours, fonts, size presets, order, add/duplicate/delete block** — by hand in a side panel, and by chat with the selected block as a chip. **No free x/y canvas** (does not translate to responsive web).
4. **Conversion: deterministic assembler + optional AI polish.** Every block type is a real hand-built component; assembly is pure code and cannot fail. The polish pass (motion, micro-detail) is bounded and soft-fails back to the assembled site (guaranteed by the 2026-10-02 `acceptIfBuildable` work).

## Architecture

### One assembler, two jobs
The assembler maps `sketch.json` → real source files (`components/home.tsx`, `styles/globals.css`, …) in the existing Next-source contract. It serves:
- **Live preview while editing.** Each hand edit PATCHes the sketch; the API re-assembles and the Studio sandbox re-renders (~1–2 s, no model, no credits).
- **Final build.** "Construir mi sitio" saves the same assembler output as a revision through the existing accept pipeline (`acceptCandidate`: kit CSS, commerce mounts, preflight all unchanged).

Because preview and build share one code path, the built site cannot drift from the approved sketch.

### Components
- **Block library** (new, likely `packages/store-templates` or sibling): ~10 parameterized block components v1 — `hero`, `marquee`, `catalog`, `story/editorial`, `reviews`, `faq`, `banner-cta`, `newsletter`, `gallery`, `footer` (+ `split-feature` if cheap). Variants per type (e.g. hero: photo-right / full-bleed / stacked). Styling via palette tokens + font ids + size presets; commerce blocks mount the existing runtime (`commerce.js`), protected elements untouched.
- **Sketch schema** (new, API + shared types): zod/class-validator; invalid values are *repaired*, never rejected (unknown font → nearest catalog font; bad colour → nearest palette role; unknown block type → dropped with a note).
- **Sketch generation** (YAPI): one structured-output call (`json_schema`, strict) with the brief, catalog and uploaded photos; assigns photos to blocks. Persisted like a checkpoint on the store draft (survives reloads; no model needed to edit).
- **Studio Boceto mode**: sandbox preview of assembled sketch; click block → panel (inline text, photo swap from uploads, bg from palette, font from catalog, size S/M/L/XL, move/duplicate/delete); «+ Añadir bloque» gallery. Reuses `source-selection.ts` chips + quick actions and `source-direct-editor.ts` patterns, retargeted at sketch blocks.
- **Chat-on-sketch**: chip = block id; the model edits the sketch JSON (small call). Invalid reply → auto-repair or keep previous sketch. No visible errors in the whole sketch loop.

### Error policy (program-wide)
The sketch loop may never surface an error to the merchant. Generation retries/repairs silently; assembly is pure and tested; polish soft-fails. The only merchant-visible failure mode allowed is the existing one on the *optional* polish pass, phrased as "keeping your approved design".

## Sub-projects (each: spec → plan → build)

1. **Sketch schema + block library + assembler.** Schema, repair rules, ~10 blocks with variants, assembler to Next-source files. Golden tests: every valid sketch assembles, compiles (`compileNextPreview`) and screenshots at 1280/390 (`captureAgentDraft`). Foundation; no UI.
2. **YAPI generates sketches.** Structured-output call, photo assignment, persistence on the store draft, wire into new-store/redesign routing in `source-chat`/`source-generation`.
3. **Studio Boceto mode.** Preview + hand-editing panel + add-block gallery + instant re-assembly loop.
4. **Chat-on-sketch + Construir mi sitio.** Chip targets a block; tiny JSON-edit calls; build saves a revision through `acceptCandidate`; optional polish pass (agent engine, soft-fail guaranteed).

Build order: 1 → 2 → 3 → 4. Sub-project 1 first — zero UI risk, everything else depends on it.

## Constraints and reuse (found in the repo)

- 21 plantillas already contain most block patterns; mine them for the v1 components rather than designing from scratch.
- Protected commerce elements (price, buy button, option pickers, pagosYa seal) keep their rules; blocks style *around* them. The trust strip ("Retiro en tienda / Pago seguro") remains runtime-owned for now (its variety is the separate themed-product-card follow-up).
- 29 self-hosted fonts (`source-font-catalog.ts`), Design DNA palette machinery, `compileNextPreview`, `acceptCandidate`, the preview sandbox, uploads — all reused as-is.
- The look target is the owner's Figma reference: strong per-section colour blocks, very large display type, product cards that differ, full-bleed photos.

## Success criteria

- A new-store prompt yields an editable sketch in ≤ 30 s, with zero possible merchant-visible errors.
- Hand edits reflect in the preview in ≤ 2 s and cost no credits.
- "Construir mi sitio" always succeeds and matches the sketch.
- Sketch generation across the 10-prompt everyday brief set: 10/10 valid (post-repair) sketches.
