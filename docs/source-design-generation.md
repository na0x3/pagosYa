# Storefront design generation

New sites and explicitly requested full redesigns use a separate, budgeted planning call through `source-design-planner.ts`. The planner develops three concepts without seeing the server's sampled index. The implementation call receives only the chosen concept, so it cannot tailor the same preferred idea to whichever index it was told to select. `design-direction.json` preserves all three proposals and the server's selection. Implementation and repair responses cannot overwrite that decision. Local edits skip planning and retain the saved direction.

There is no required homepage hero, section sequence, palette, font pairing or product-card composition. Confirmed merchant choices and real assets still guide the design. New sites and full redesigns now use Next.js, React, TypeScript and Tailwind CSS. Explicit redesigns can migrate legacy HTML into React components; ordinary edits retain the existing preservation rules. The saved site's visual direction is supplied as an anti-reference during a redesign and as a reference during local edits.

## Plan fidelity

Each new concept includes `layout.sections` (invented IDs for the direct content blocks in `main`), `catalogSection`, `standaloneIntro` and `productsInOpening`. These describe the chosen composition; they are not a shared page template. Runtime contact, subscription, return-visit, cart and status slots are excluded from the block list.

Each concept also follows the homepage action hierarchy: one dominant filled CTA in the opening, no more than two quiet secondary destinations nearby, and no large button cluster for navigation. Substantial story, location, contact, gallery, promotion, or FAQ content should use a real page and a relative anchor from the shared navigation or footer. A browser probe reports this as a design warning when a rendered opening still contains competing action controls; it does not block a merchant's deliberate design request.

The server inspects literal JSX structure for React projects and parses generated HTML for legacy projects, without executing authored modules. React files also pass TypeScript checking and browser compilation. Missing/reordered blocks, an extra introduction outside the plan, or a catalog in the wrong block enter the existing single source-repair path. Old saved directions without layout metadata remain readable and editable.

Studio separately checks rendered evidence at 1280, 768, 390 and 320 CSS pixels. A concept promising products in the opening must show a real product's name, price and add action without scrolling. A concept explicitly choosing no independent introduction has a 320 CSS-pixel budget before its catalog starts; this catches a large hero disguised inside the catalog block. This conditional check does not limit concepts that choose an independent introduction. Studio also flags a mobile header cart hidden inside navigation and unusually tight heading tracking. Decorative boxes crossing product text, a price displaced to a distant column/row, and tight product headings produce advisory findings with concrete repair evidence. Clipped purchase controls are functional failures, including clipping hidden by an ancestor; horizontal scroll containers are treated separately. Artwork checks inspect explicit data-product-decoration/aria-hidden elements and text ranges, so decorative backgrounds, pseudo-elements and unusual compositions still need visual judgment. These are not an originality score or an automatic paid retry.

## Typography

The generator can choose local Bricolage Grotesque, Fraunces and Instrument Sans variable fonts, alongside uploaded merchant fonts and appropriate system families. Only referenced bundled fonts and their SIL Open Font License files enter an export. Generated pages declare their own `@font-face` rules and load no remote font service. Uploaded/confirmed brand typography takes precedence.

Original files, source URLs, Git blob identifiers and checksums are retained in `apps/api/src/stores/source-kit/fonts/provenance.json`. Sources: [Bricolage Grotesque](https://github.com/google/fonts/tree/main/ofl/bricolagegrotesque), [Fraunces](https://github.com/google/fonts/tree/main/ofl/fraunces), [Instrument Sans](https://github.com/google/fonts/tree/main/ofl/instrumentsans).

## Product compositions

An optional `template[data-pagosya-product-template]` provides one root element, placed outside the live catalog mount. Required descendants are `data-product-field="name"`, `data-product-field="price"`, `a[data-product-link]` and `button[data-product-add]`. Optional fields are `description` and `image` (on an `img`). The runtime clones the template and supplies real catalog values, stock state, product navigation and option selection. Invalid templates fall back to the default card and surface an advisory browser finding.

Custom roots receive `data-custom-product` and `.menu-item`; the default card's forced overlay and purchase-button positioning do not apply. Authors control their composition. Every `a[data-product-link]` is bound to its own product, including secondary detail links. On activation the runtime restores the item ID before sandbox navigation, protecting against presentation code that normalizes URLs. Missing images mark the root `data-no-image`, hide optional `data-product-media` wrappers and hide empty image-only links. Authors can collapse reserved media columns with that state. Empty categories and redundant descriptions are hidden.

Empty status surfaces consume no space while retaining the live-region node for later messages. Product details without photos use a single information column. Initially empty cart mounts stay hidden until the drawer opens, while deliberately authored inline cart content is preserved. Runtime-owned cart slots authored as dialogs are normalized to avoid nesting closed dialogs inside the cart drawer; redundant sibling reviews on standalone checkout pages are hidden so the active checkout shows one payment form.

## Review and cost

Studio checks rendered desktop and mobile pages in isolated frames. Empty heading-only sections, unmatched catalog grid/list selectors and invalid custom templates produce advisory findings. These heuristics are not a visual quality score or a guarantee of originality. Functional failures still block publication; design findings prepare an editable repair message and do not initiate paid calls.

Creation/redesign normally uses two provider calls: exploration and implementation. Both consume the same request budget and timeout. A compact implementation allowance is reserved before paying for exploration; planning cannot consume the entire remaining budget. One repair is shared between planning and implementation within that same budget. A completed but invalid plan receives one correction with an actionable diagnostic; if used, implementation has no additional repair. Failed network/quota calls or incomplete planning responses stop before code generation. User credits on a successful revision include both successful phases; failed attempts are absorbed, unknown usage is not fabricated, and a failed revision consumes zero user credits. Provider usage is recorded separately for each phase. Validation errors identify missing files, commerce hooks and layout mismatches. There are no unlimited automatic retries.

Verification: API tests cover concept validation, metadata persistence, redesign authorization, preservation and budgets. Browser tests cover custom cards, stock, configurable products, simulated payment, advisory diagnostics and preparing a repair without a generation request. Synthetic live samples and screenshots are recorded under `tmp/source-design-diversity-20260909` and `tmp/source-design-final-20260909`; they use no merchant data or real payments.

The implementation comparison adds `tmp/source-design-contract-20260909` (intermediate single-call batch) and `tmp/source-design-planned-20260909` (separate planning, per-business folders). The benchmark supports `--cycle-concepts --repeats 3` to cover all selected indexes, `--open-direction` to remove preset styling from the fixture, and a `breakfast` case using the repository's existing AI breakfast illustration as disclosed synthetic input. It records source/generator digests, committed concepts, font and catalog measurements, functional results and design-check results separately. Use `--recheck` for saved sources without new model calls; a passing automated check still requires visual judgment.

Final results and remaining defects: [September 9 validation](SOURCE_DESIGN_VALIDATION_2026-09-09.md). The last replay additionally follows every generated product-detail link, rather than testing only direct product URLs.

The follow-up [layout repair report](SOURCE_DESIGN_REPAIRS_2026-09-09.md) contains original/repaired comparisons. Studio can prepare corrections from both blocking failures and visual warnings, prioritizing failures and preserving the current direction; preparing the message does not submit a generation.

The BURGUERIA browser review exposed unequal intrinsic photo heights, an over-cropped portrait carousel, and horizontal flex applied to text with line breaks. Generation guidance now covers these concrete failure modes. The browser reports measured overflow dimensions and warns when a carousel using `cover` retains less than 45% of an image's area; this is an advisory crop check, not a judgment about the subject or artistic intent.

Generated revisions are saved as drafts. Studio waits for its isolated browser checks before finishing the generation action and displays the current revision's results in the chat. Errors and visual findings can populate a correction request, and up to eight current, revision-matched findings accompany the next merchant request as diagnostic data. Stale results and pending catalog setup are excluded. This does not automatically trigger another paid generation or perform screenshot-based visual review; final appearance still requires inspection.

An unavailable catalog produces one `skipped`, blocking setup result instead of repeated purchase failures on every page and viewport. It remains impossible to publish through Studio until an available product permits the purchase checks. Missing products are never invented to satisfy the tests.


## Next.js source and previews

`SOURCE_FRAMEWORK=next` is the default for new sites and explicit full redesigns. Existing static sites retain their format during ordinary edits. A saved framework marker keeps subsequent React edits on the React path even if the default is changed to `static`.

YAPI authors `components/**/*.tsx` and `styles/globals.css`; the platform supplies the Next.js Pages Router scaffold, pinned dependencies, Tailwind configuration, and commerce bridge. Home, product, and checkout are separate pages with reusable React components. Generated components can import React and local components. Server APIs, arbitrary packages and user-authored build configuration are outside this generator contract.

Studio and the hosted iframe use compiled React bundles and generated Tailwind CSS from those same source components. The API never imports or renders merchant React modules. It checks types, validates literal hooks and planned main-section structure, and compiles in memory. Dynamic rendering still needs the existing isolated browser checks. Generated bundles have a bounded 800 KB per-file allowance; the overall 8 MiB snapshot limit still applies. Code mode exposes the authored components and stylesheet; saving rebuilds the preview atomically and failed compilation preserves the saved revision.

ZIP downloads contain a runnable Next.js project: `npm install`, `npm run dev`, `npm run typecheck`, and `npm run build` (static output in `out/`). `npm start` serves the built export. Next.js prerenders the page layout; the existing PagosYa runtime starts after React hydration and owns catalog, cart and payment mounts. Uploaded images/fonts, current commerce/privacy/motion code, brand CSS and SEO metadata are included. Local page links preserve the cart through full document navigation. The PagosYa backend remains responsible for live commerce.

This implementation changes the authoring stack; it does not promise better visual quality by itself. It does not run a merchant Next server in the API or migrate every saved site automatically. Reference-site inspection remains HTML/CSS inspection rather than rendered-browser reference capture.
