# Security audit — 2026-10-29

Scope: `apps/api` (NestJS), the checkout app's customer account client, the storefront kit's browser storage, and production
dependencies. Method: read the global bootstrap, list every controller and its guards, review each public (unauthenticated)
route, the payment webhooks, uploads, KYC documents, customer accounts, order tracking, inbound integrations and payment
confirmation, scan guarded routes for `storeId`/`id` parameters that never receive the caller, and run `pnpm audit --prod`.

## Medium

**M1 — Baneco QR webhook trusts a static shared header** (`payment-intents/baneco-qr-webhook.controller.ts`).
The secret is compared in constant time and the route fails closed when it is unset, and `applyCallbackResult` rejects a
wrong amount or currency, so a forged notice cannot mark a different amount paid. But anyone holding the header value can
mark a pending intent of the exact amount as paid, and there is no replay window or source check.
*Recommendation:* before marking `succeeded`, query Baneco's payment status for that `qrId`; add an IP allowlist at the edge;
rotate `BANECO_WEBHOOK_SECRET` with the bank. Needs Baneco's API details — owner/bank decision.

**M2 — published stores may share one browser origin.** Custom domains point at one storefront app
(`CUSTOM_DOMAIN_CNAME_TARGET`, default `stores.pagosya.bo`). If stores without a custom domain are served as paths of one
host, every store's JavaScript — written by YAPI or edited by the merchant in the Studio — shares `localStorage` /
`sessionStorage` with every other store on that host (carts, saved lead emails, dismissed popups). Customer sessions are
**not** exposed: they live in the checkout app on its own origin. *Recommendation:* serve each store on its own subdomain
(`<slug>.stores.pagosya.bo`) or keep storage keys per store and add a CSP to published stores. To verify against the
production hosting before launch.

## Low

**L1 — withdrawn.** The first pass flagged that a deleted customer could not register again with the same email. On
checking `deleteAccount`, the deleted row's email is anonymised to `deleted-<id>@deleted.invalid`, which frees the
`(storeId, email)` key; registration works. No finding.

## Controls verified as sound

- **Bootstrap:** helmet; `Content-Security-Policy: default-src 'none'` on every API response; `Cache-Control: no-store`;
  strict `ValidationPipe` (whitelist, forbid unknown); CORS allowlist + verified custom domains, `credentials: false`;
  global throttling (120/min, 7,200/h, Redis-backed when configured); 1 MB JSON limit, JSON depth/complexity guard;
  415 for unexpected content types; request/header timeouts.
- **Payment webhooks:** Baneco header secret (timing-safe, fails closed); dLocal signature + `X-Date`; amount and currency
  must match the PaymentIntent; repeated notices are idempotent.
- **Payment confirmation:** `ClientSecretGuard` binds the client secret to the `:id` in the path.
- **Uploads:** MIME allowlist (no SVG/HTML), magic-byte check against the declared type, size caps per type, pixel/dimension
  bombs refused, random UUID names, `nosniff`.
- **KYC documents:** private storage, ops-only viewing behind `OpsAuthGuard`, every view audit-logged.
- **Storefront customers:** argon2 passwords, 256-bit random tokens stored as SHA-256, constant-time dummy hash for unknown
  emails, sessions bound to their store, per-route throttles; registration never overwrites a verified account.
- **Order tracking:** signed tokens, fails closed without `ORDER_TRACKING_SECRET`.
- **Inbound integrations:** per-connection secret verified with argon2, throttled.
- **Ops routes:** class-level `OpsAuthGuard` on domain orders, settlement and limits.
- **Secrets:** `.env` files are git-ignored and were never committed; only `.env.example` is tracked.
