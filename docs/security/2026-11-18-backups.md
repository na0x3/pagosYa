# Respaldos y prueba de restauración (ISO 27001 M-10)

**Estado (2026-11-18):** procedimiento construido y probado en local. Falta ejecutarlo contra la base de producción
cuando exista (no hay configuración de despliegue en el repositorio).

## Política

| Qué | Cómo |
|---|---|
| Respaldo | Diario, `pg_dump` en formato *custom* de toda la base. |
| Cifrado | AES-256-GCM con `BACKUP_ENCRYPTION_KEY`, guardada en el gestor de secretos, nunca junto al respaldo. |
| Lugar | Almacenamiento de objetos de otra cuenta/región, con bloqueo de escritura (*object lock*) de 30 días. |
| Retención | 30 días de diarios; el primero de cada mes se conserva 12 meses. |
| Prueba | Mensual y después de cada cambio de esquema grande: `scripts/backup-restore-check.mjs`. El informe se guarda en `docs/security/backup-restore-checks/`. |
| Objetivos | RPO 24 h (un respaldo diario); RTO 2 h para restaurar y apuntar la API a la base restaurada. |

## La prueba

```
SOURCE_DATABASE_URL=…  RESTORE_ADMIN_URL=…/postgres  BACKUP_ENCRYPTION_KEY=…  \
  node scripts/backup-restore-check.mjs --report docs/security/backup-restore-checks/AAAA-MM-DD.md
```

1. Respalda la base de origen (solo lectura).
2. Cifra el respaldo y lo vuelve a abrir, como se haría con el archivo guardado fuera.
3. Lo restaura en una base nueva y temporal.
4. Compara el número exacto de filas de cada tabla y recalcula la cadena de hashes del registro de auditoría (M-04).
5. Borra la base temporal y escribe el informe. Sale con código 1 si algo no coincide.

Primera ejecución: `backup-restore-checks/2026-11-18-drill.md` (local, 167 tablas, cadena de auditoría intacta). En la
misma sesión, la prueba sobre una base con una entrada de auditoría alterada a propósito salió **FAILED**, como debe.
